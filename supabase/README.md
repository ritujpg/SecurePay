# SecurePay local Supabase demo

The application reads and writes Supabase records through `/api/demo-db`; browser code does not create a Supabase client or query tables directly. The API is mounted only by the Vite development server and is additionally restricted to loopback requests. The Vite dev server binds to `127.0.0.1`. The production server does not mount these routes.

Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` in the local `.env` file for the existing read and non-transaction demo operations. The atomic transaction RPC additionally requires `SUPABASE_SERVICE_ROLE_KEY`, read only by the server, because the RPC is executable only by `service_role`. Never put this key in a `VITE_` variable, frontend code, or a browser request. The transaction endpoint remains localhost-only and is disabled in production. The backend chooses the earliest-created synthetic `users` record as the demo profile; the existing login remains a local simulation and is not Supabase Auth.

The migration `migrations/20261117220000_atomic_demo_transactions.sql` adds a request ledger, `create_demo_transaction_atomic`, and `update_demo_transaction_status_atomic`. The ledger stores a SHA-256 payload hash rather than a second copy of the transaction details. It does not alter existing tables, constraints, indexes, or RLS. The migration file has not been applied to Supabase; apply it to the intended project before using transaction writes. Transaction creation and its risk assessment, security check/activity, and status-dependent alert/check/activity are written in one database transaction. Concurrent requests using the same key serialize; an identical retry returns the prior transaction, while a different payload is rejected. The status route also changes the row and its matching security records atomically. `security_checks` remains unlinked by transaction ID because that column does not exist.

**Security limitation:** Row Level Security is disabled. The anon key is not privileged, but without RLS the database does not provide a row-level security boundary. The loopback-only API is suitable only for local synthetic-data demonstrations; it is not production security and must not be deployed or exposed to a network. Enable and verify RLS policies and add real authentication/authorization before any production integration. This migration file contains no RLS changes and has not been applied; it does add execute/table privileges for the new RPC and its ledger only.
